# CVM: CWhip Virtual Machine

CVM is a portable stack virtual machine project implemented in CWhip. Its
approved v1 bytecode format and assembly syntax are described in the
[specification](doc/BYTECODE-ASSEMBLY.md).

The versioned `cvm` shared bytecode
package (`CVM`, version `1.0.0`) provides canonical v1 format/opcode
definitions, checked byte readers and writers, instruction and container
builders, and structural validation. The package is installed under
`share/cwhip/modules/cvm/1.0.0` for import by other CWhip applications.

The standalone `cvm-as` assembler uses a CVM-owned grammar generated by the
separately installed cparsegen executable at build time. It resolves named
operands and forward references, emits through the shared library, and writes
binary files through public SDK byte APIs. The reusable `cvmfile` package
provides the same file boundary for loaders. The installed `cvm-run` command
and `cvmrun` package execute validated containers with checked runtime
semantics and configurable resource limits. See
[Interpreter usage and scope](doc/INTERPRETER.md).

The interpreter supports all v1 instructions and host services, with
configurable console/filesystem capabilities and resource limits. A
disassembler and the SmallC backend are not included. Structural validation
and runtime checks are distinct; neither claims a security boundary. The full
shared-library boundary and APIs are documented in
[the bytecode library guide](doc/BYTECODE-LIBRARY.md).

See [Assembler usage and contract](doc/ASSEMBLER.md). The template
`src/main.cw` hello-world remains as a build-shell example.

With a current CWhip SDK selected and `cparsegen` on `PATH`, run
`scripts/setup [--clean] [debug|release|profile]` to configure and enter the
project shell. Then use `build`, `rebuild`, or `clean`; `--clean` removes
the previous generated outputs before configuring.

See [Building](doc/BUILDING.md) for prerequisites, SDK selection and output-directory
customization, and [Project shell](doc/PROJECT-SHELL.md) for the shell
environment and available commands. See the [changelog](doc/CHANGELOG.md) for
implementation history.
